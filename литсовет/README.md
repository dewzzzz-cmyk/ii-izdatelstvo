# Литсовет

ИИ-инструмент для написания прозы: многоагентный пайплайн (Архитектор → Прозаик ⇄ Оценщик → Стражи → Линейный редактор) с авторским контролем, памятью канона и экспортом в EPUB/DOCX/MD.

Рабочая версия развёрнута на Railway: **https://litsovet-v2-production.up.railway.app** (подробности — в разделе «Где развёрнута рабочая версия»).

## Установка на компьютер (Windows 10/11)

Готовый архив: **`Литсовет-установщик-<версия>.zip`** — лежит на рабочем столе
того, кто его собирал, и пересобирается командой ниже.

1. Распаковать архив целиком (правой кнопкой — «Извлечь все»). Запускать
   установщик прямо из zip нельзя: рядом должна лежать папка `app`.
2. Двойной щелчок по **`УСТАНОВИТЬ ЛИТСОВЕТ.bat`**.
3. Программа проверит Node.js (при отсутствии предложит поставить сама),
   спросит папку — по умолчанию `%LOCALAPPDATA%\Litsovet` — и создаст ярлык
   «Литсовет» на рабочем столе и в меню Пуск.
4. Запуск — по ярлыку. Откроется `http://localhost:8788`. Окно консоли, которое
   при этом появляется, и есть сервер: пока оно открыто, программа работает.
5. Ключ API впишите в Настройках при первом запуске. Он хранится только в памяти
   вкладки и после перезагрузки страницы вводится заново — так задумано.

Удаление — `УДАЛИТЬ ЛИТСОВЕТ.bat` в папке установки. Спросит подтверждение
словом, затем отдельно — оставить ли книги.

Пересобрать архив (нужен Python 3):

```bash
python installer/build-installer.py
python installer/zip-installer.py "%USERPROFILE%\Desktop\Литсовет-установщик.zip"
```

Подробности — [installer/README.md](installer/README.md): что попадает в
дистрибутив, почему bat-файлы в CP866 и как это проверялось.

## Запуск из исходников

**Windows:** дважды кликните `deploy.bat` (проверит Node.js, запустит сервер, откроет браузер).

**Linux/macOS:**
```bash
chmod +x start.sh
./start.sh
```

**Вручную:**
```bash
node server.js
```

Откроется `http://localhost:8788` (порт можно переопределить переменной `PORT`).

Требуется Node.js 18+, https://nodejs.org — зависимостей и сборки нет.

## Данные

Проекты хранятся в браузере (IndexedDB) + синхронизируются на диск в `data/projects/` для доступа с других устройств. API-ключ никогда не сохраняется на диск — только в памяти браузера на время сессии.

## Перенос на другой компьютер

Запустите `build-deploy.bat` — соберёт архив на рабочем столе. На новом компьютере распакуйте и запустите `deploy.bat`.

## Где развёрнута рабочая версия

Приложение выложено на **Railway** и доступно по адресу:

**https://litsovet-v2-production.up.railway.app**

| Что | Значение |
|---|---|
| Проект Railway | `litsovet-v2` (`a8104dae-1f66-43e4-bc02-f73009792b1b`) |
| Сервис | `litsovet-v2` (`d2e9dd56-dff7-4081-8fbc-374a4f280648`) |

| Постоянный диск | том `litsovet-v2-volume`, смонтирован в `/data` |
| Переменная `DATA_DIR` | `/data` — **обязательна** |
| Порт | Railway подставляет свой в `PORT`; сервер его читает |

### Как выложить новую версию

Из папки `литсовет/`:

```bash
railway up --detach
```

Три вещи, на которых легко обжечься:

1. **`git push` НЕ разворачивает приложение.** Автодеплой из репозитория не настроен: коммит уходит в git, а на сервере остаётся прежний код. Разворачивает только `railway up`.

2. **Версию для проверки читает `package.json`, а не `APP_VERSION`.** `GET /api/version` отдаёт `version` из `package.json`. Если поднять только `APP_VERSION` в `src/state.js`, задеплоенное приложение будет представляться старой версией, и вы не поймёте, доехал деплой или нет. Поднимайте оба.

3. **Проверяйте, что деплой доехал**, а не что команда отработала — сборка идёт несколько минут:

```bash
curl -s https://litsovet-v2-production.up.railway.app/api/version
```

### Данные на сервере

Всё лежит на томе в `/data`:

| Папка | Что там |
|---|---|
| `/data/data/projects/` | книги (по файлу на проект) + `_index.json` — лёгкий список для настроек |
| `/data/data/backups/` | предыдущие ревизии книг: 5 последних на проект, потолок 300 МБ на папку |
| `/data/data/conflicts/` | снимки правок, отбитых по конфликту ревизий |
| `/data/checkpoints/` | экспорт-чекпоинты, если их делали вручную |

**Без переменной `DATA_DIR` данные лягут внутрь контейнера и сотрутся при первом же деплое.** Это уже случалось.

API-ключ на сервер не уходит: он живёт только в памяти вкладки браузера и вырезается при синхронизации. После перезагрузки страницы его нужно ввести заново — это не сбой, а устройство.

### Если книга испорчена

В настройках у каждой книги, которая есть на сервере, кнопка **🕘** — список сохранённых ревизий с датой и размером. Выбор номера возвращает книгу к этой версии, причём текущее содержимое тоже уходит в историю, так что откат обратим.

## Тесты

```bash
npm test
```

Встроенный `node --test`, ни одной зависимости. Покрыты разборщики ответов
модели и инварианты, которые уже ломались: `extractJSON`,
`parseDebateRevision`, `parseSceneSummary`, `looksTokenTruncated`,
`validateSkeleton`, `findGhostCharacters`, `lineEditMessages`,
`rememberRejected` и другие.

Отдельно есть стенд — проект с заранее заведёнными поломками, чтобы не
проверять их на живой книге:

```bash
node test/seed-stand.mjs http://localhost:8788
```

## Соглашение: сбой не сообщается через `null`

Больше половины багов этого проекта имели одну форму: функция возвращала
`null` при неудаче, а вызывающий принимал это за успех и шёл дальше. Наглядный
случай — сцена помечалась «Готово» без сводки в памяти, и следующие сцены
писались вслепую к её событиям.

Правило для нового кода:

- функция, которая может не справиться, **бросает исключение** (как
  `proofreadText` при отсутствии ключа) либо возвращает `{ ok:false, reason }`;
- если `null` всё же используется как «не получилось» (так устроены
  разборщики: `extractJSON`, `parseSceneSummary`, `parseEvaluator`), то
  **каждый** вызывающий обязан его проверить и сказать автору, что именно не
  вышло и чем это грозит. `try { await f() } catch {}` вокруг такой функции —
  не защита: `null` не бросает, и `catch` не сработает никогда.
