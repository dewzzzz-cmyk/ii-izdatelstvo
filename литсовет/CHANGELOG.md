# Changelog

Версия видна в приложении (шапка и «Настройки») и через `GET /api/version`.
Бампается при каждом серьёзном фиксе пайплайна/сервера — не при мелкой
правке промпта или косметике UI.

## 1.25.0 — 2026-07-25

- **Найдена и исправлена реальная причина баннера «на сервере более новая
  версия» после каждой правки.** На 409 (конфликт ревизий) клиент отбрасывал
  `serverRev` из ответа и просто продолжал слать свой старый `rev` дальше —
  сам от этого никогда не восстанавливался. Хуже: debounce (400мс) защищал
  только от повторного ПЛАНИРОВАНИЯ пуша, не от гонки — на реальной сети
  (не localhost) ответ сервера иногда занимал больше 400мс, и следующая
  правка запускала ВТОРОЙ `persistToServer()` параллельно с ещё не
  завершившимся первым; второй уходил со старым `rev` (первый ещё не успел
  его обновить своим ответом) и получал 409 от собственной же вкладки —
  отсюда «баннер вылезает после каждой правки». Пуши теперь идут строго
  последовательно (`runPersist` встаёт в хвост промис-цепочки, не летит
  параллельно) — самоконфликт одной вкладки больше невозможен; баннер
  остаётся только для настоящего конфликта (другая вкладка/устройство
  реально сохранили более новую версию).
- **Баннер синхронизации уменьшен и получил кнопку закрытия** — по прямой
  просьбе автора: раньше на всю ширину экрана, без возможности скрыть иначе
  чем перезагрузкой страницы. Теперь компактная плашка в углу с ✕.
- **По прямой просьбе автора (живой инцидент: «Оценщик: ответ не
  распарсился... лимит был 3840 — повтор с лимитом 7680») — дефолтный
  потолок токенов поднят на 50% сразу у ВСЕХ ролей пайплайна**, не только
  Оценщика (Архитектор сцены, Прозаик, Оценщик, все Стражи, Линейный
  редактор). Пятый раунд этого же одноразового миграционного паттерна —
  проекты, ещё сидящие на прошлом дефолте, подтягиваются автоматически;
  вручную поднятые слайдеры не трогаются.

## 1.24.0 — 2026-07-25

- **Добавлен Claude (Anthropic) как провайдер.** Клод использует другой API,
  не OpenAI-совместимый `/chat/completions` — своя эндпоинт-схема
  (`/v1/messages`), заголовки (`x-api-key`+`anthropic-version`, не
  `Authorization: Bearer`), формат запроса (system — отдельное поле, не
  `messages[role=system]`; `max_tokens` обязателен) и формат SSE-стрима
  (`content_block_delta` с `delta.text`, не `choices[0].delta.content`).
  `server.js` получил отдельную ветку `handleAnthropicGenerate()` —
  определяется по `baseURL` (`api.anthropic.com`), переводит usage
  (`input_tokens`/`output_tokens`) в формат, который уже понимает клиент
  (`prompt_tokens`/`completion_tokens`), не трогая общий путь для остальных
  провайдеров. Добавлены модели (`claude-opus-4-8`, `claude-sonnet-5`,
  `claude-haiku-4-5`) в `providers.js` (общий список для Настроек и
  per-роли — см. 1.23.0) и цены в `PRICES` (`state.js`), чтобы счётчик
  расхода не считал Клода по тарифу DeepSeek по умолчанию.
  **Важно (объяснено в UI рядом с полем ключа в Настройках):** нужен
  платный API-ключ с console.anthropic.com (pay-as-you-go) — подписка
  Claude.ai Pro/Max программного доступа не даёт, её ключ здесь не подойдёт.
  Живая проверка: запрос через `/api/generate` с `baseURL:
  api.anthropic.com` и заведомо неверным ключом дошёл до реального
  `api.anthropic.com/v1/messages` и вернулся с настоящей ошибкой
  `authentication_error` (не «эндпоинт не найден» и не ошибкой формата
  запроса) — подтверждает, что маршрутизация, заголовки и тело запроса
  собраны верно.

## 1.23.0 — 2026-07-24

- **Переопределение модели/провайдера по роли — теперь выбор из списка, не
  свободный текст, а ключи живут только в Настройках.** По просьбе автора
  переделан 1.22.0: там per-роль оверрайд был тремя текстовыми полями
  (модель/URL/ключ) прямо в панели агентов — ключ приходилось вводить
  заново на каждой роли, и ничего не мешало опечататься в URL. Теперь:
  - Новый общий модуль `src/providers.js` — единый список известных
    провайдеров (DeepSeek/OpenAI/Gemini/Qwen) и их моделей, используется и
    в Настройках, и в панели агентов, и в `llmFor()`.
  - В панели агентов (⚙ у роли → «🔌 Модель/провайдер для этой роли») —
    два выпадающих списка: Провайдер и Модель (с «✎ другая модель…» для
    редких случаев). Свой URL/ключ здесь больше не спрашиваются.
  - В Настройках — новый блок «Ключи других провайдеров»: по одному полю
    на каждого известного провайдера, сохраняются в `global.apiKeys`
    (по имени поля совпадает с уже существовавшим `SECRET_KEYS` в
    storage.js — как и одиночный `apiKey`, никогда не уходит на диск/сервер,
    восстанавливается из localStorage при загрузке). Ключ текущего
    провайдера из основного поля тоже автоматически туда попадает — ничего
    вводить дважды не нужно для самого частого случая.
  - `llmFor(state, agent)` резолвит URL/модель по `agent.provider` из
    providers.js, ключ — из `global.apiKeys[agent.provider]` с откатом на
    `global.apiKey`, если это тот же провайдер, что выбран по умолчанию.
  - Живая проверка (dev-сервер, инъекция состояния через консоль): Прозаик
    с `provider:'openai', model:'gpt-4o'` резолвится в
    `baseURL: api.openai.com/v1, model: gpt-4o, apiKey: <ключ OpenAI из
    Настроек>`, а Оценщик без оверрайда — в глобальный DeepSeek-конфиг, как
    и раньше. Оба сценария подтверждены через прямой вызов `llmFor()` в
    браузере, не только чтением кода.
- **Панель агентов: «✓ Включить все» / «✕ Выключить все».** По просьбе
  автора — раньше приходилось щёлкать тумблер каждого из 16 агентов по
  одному, чтобы временно отключить всех. Кнопки действуют на агентов
  ТЕКУЩЕГО фильтра (Все/Основные/Стражи/Мои), не обязательно на всех сразу.

## 1.22.0 — 2026-07-24

- **Переопределение модели/провайдера ПО РОЛИ, не только глобально.**
  Раньше весь пайплайн (Архитектор сцены, Прозаик, Оценщик, все Стражи,
  Линейный редактор, Книжный архитектор) был жёстко привязан к ОДНОЙ
  модели из общих настроек (`state.global.model/baseURL/apiKey`) — не
  было способа посадить, например, Прозаика на более сильную/дорогую
  модель, оставив Стражей и Оценщика на дешёвой. Разбор живого случая
  (сравнение прозы Литсовета с текстом от другого ИИ по тому же брифу)
  показал, что реальным потолком качества чаще оказывается сама модель
  (проект стоял на `deepseek-chat`), а не бюджет токенов или промпты —
  но сменить модель можно было только для всего пайплайна разом.
  Теперь у каждой роли в панели агентов (⚙ → раскрыть роль) есть
  свёрнутый блок «🔌 Модель/провайдер для этой роли»: три поля (модель,
  URL API, ключ), все опциональные — пустое поле наследует общие
  настройки, заполненное перекрывает их только для этой роли. Действует
  в автопайплайне (`runScene`), ручном прогоне одного агента (▶),
  точечной правке (patchScene — использует конфиг Прозаика) и в Книжном
  архитекторе (генерация и точечная правка скелета).

## 1.21.2 — 2026-07-24

- **По просьбе автора: литературные стражи (голос/стиль/юмор/POV/диалог/
  развязка/атмосфера/читатель) теперь запускаются с ПЕРВОЙ итерации

  дефолте 5, на новый дефолт 3 (ручные значения не трогает).

## 1.21.1 — 2026-07-24

- **«Улучшить структуру» больше не крутит 3 прогона без спроса — по
  умолчанию один.** Живой инцидент: за один клик «Улучшить» автоматически
  прогнало `structureMaxIter` (было 3) внутренних итерации подряд, и
  книга усохла с ~90к до ~70,6к слов (17→11 глав, 52→44 сцены) — откат по
  баллу Оценщика (см. ниже) это не ловил, потому что Оценщик судит
  архитектуру, а не объём. Дефолт `structureMaxIter` понижен 3→1 (с
  одноразовой миграцией для проектов, ещё сидящих на старом дефолте) —
  кто хочет автоматических повторов, поднимает слайдер «Прогонов
  структуры» сам.
- **Новый автооткат: похудение книги при «Улучшить» — та же защита,
  что уже была на счёт балла, только по объёму.** Откат по баллу
  Оценщика существовал, но объём (сумма targetWords по сцене) никогда
  не проверялся — LLM мог тихо выбросить главы/сцены, формально не
  испортив архитектурную оценку. Теперь прогон, где суммарный объём
  просел больше чем на 10% относительно предыдущего состояния,
  откатывается автоматически тем же путём, что и провал по баллу.
- **Проверил и подтвердил: живое стриминг-обновление «N симв.» во время
  генерации скелета — реальные байты сетевого ответа**, не таймер:
  проследил путь от `fetch('/api/generate')` → `reader.read()` в цикле
  → `onToken(chunk)` в llm.js — каждый вызов соответствует реально
  полученному куску HTTP-ответа. У Оценщика структуры такого счётчика
  нет вовсе (не передаёт onChunk) — статичный спиннер на этом шаге не
  баг, а отсутствие фичи там, где её никогда не было.
- **Проверил: в Написание попадает не только бриф.** Явно используются
  бриф, эмоция, entryState, targetWords (как явное указание по объёму) и
  sceneType (сцена/секвель, определяет структуру сцены). При этом нашёл
  реальный пробел: `chapter.arc` (завязка/развитие/кульминация/развязка)
  — заполняется на этапе Структуры, читается Оценщиком структуры, но
  нигде не доходил до самой генерации прозы. Добавлена короткая заметка
  о положении главы в дуге книги в промпт Прозаика (context.js).

## 1.20.7 — 2026-07-24

- **КРИТИЧНО: сцена могла уйти в книгу вообще БЕЗ литературной проверки,
  а находки Стражей на поздних итерациях никак на это не влияли.**
  Живой инцидент: автор увидел, что Страж развязки два раза подряд
  (итерации 4 и 5) находит одну и ту же критическую проблему («герой
  мгновенно доверяет говорящей тени»), и она так и не исправляется к
  концу прогона. Расследование вскрыло проблему серьёзнее, чем просто
  «Прозаик не справился»: литературные стражи (голос/стиль/развязка/
  атмосфера/юмор/читатель/...) бегут только на evalAccepted или
  iter>=maxIter-1 — на ранних итерациях они физически ещё не запускались,
  и `criticals` там был пуст просто потому, что стражи ещё ничего не
  видели. В отборе «best» сравнение шло СНАЧАЛА по признаку «нет
  критических флагов», и только потом — по факту литературной проверки.
  Итог: ранняя, никогда не проверенная литературными стражами итерация
  побеждала как «самая чистая» — просто потому, что её никто не смотрел
  — над поздней итерацией, которую стражи реально проверили и честно
  нашли проблему. Симуляция на данных реального лога подтвердила: в best
  уходила итерация 2 (не проверялась вовсе), а не 4/5 (проверялись,
  найдена критическая проблема). Порядок сравнения теперь: сначала
  «проверено литературными стражами» (проверенный черновик всегда
  предпочтительнее непроверенного, даже с находками), и только среди
  одинаково проверенных — чистота и балл. Контрольные сценарии (чистый
  проверенный побеждает непроверенный; чистый проверенный побеждает
  «грязный» проверенный с более высоким баллом) подтверждены на симуляции
  перед внедрением.

## 1.20.6 — 2026-07-24

- **КРИТИЧНО: «Черновик отсутствует» — пустая правка Прозаика уходила
  Стражам и Оценщику как черновик сцены.** Живой инцидент: черновик 3
  получил «1/10 · Черновик отсутствует — предоставлен пустой текст».
  Причина — в защите от слишком короткой правки (`pRes.text &&
  pRes.text.length < prevDraft.length*0.6 ...`): `pRes.text && ...`
  ложно уже на пустой строке, так что откат к предыдущему черновику НЕ
  срабатывал именно тогда, когда правка `parseDebateRevision` вернула
  `prose=''` (узкий случай: тег [ТЕКСТ] есть, [РАЗБОР] нет, содержимого
  после тега — ноль, `parsed.truncated` его не ловит, т.к. требует
  `hasDebate`). Итог — пустая «правка» проходила дальше по пайплайну
  без отката, тратя полный вызов Стражей и Оценщика впустую и давая
  ложную оценку 1/10. Условие теперь ловит и пустой/отсутствующий текст,
  с явным предупреждением в логе при откате.

## 1.20.5 — 2026-07-24

- **КРИТИЧНО: ретрай Оценщика/Прозаика на обрыв токенами мог повторять с
  МЕНЬШИМ лимитом, чем исходный.** Живой инцидент: автор поднял слайдер
  Оценщика до 8000 (максимум слайдера) — лог показал «лимит был 8000...
  повтор с лимитом 7200». Причина: `evalRetryTk = Math.min(7200,
  evalMaxTk*2)` — жёсткая константа 7200 была ниже, чем исходный лимит
  8000, так что «повтор с увеличенным лимитом» на самом деле СНИЖАЛ его,
  гарантируя тот же обрыв повторно. Тот же паттерн (потенциально, при
  очень длинных целевых сценах) был и в ретрае Прозаика. Оба места
  теперь используют `Math.max(исходный+1, Math.min(19200, исходный*2))`
  — ретрай гарантированно не ниже исходной попытки.
- **Страж стиля молча не участвовал в разборе, если не заданы правила
  автора.** Тумблер был включён, но `styleGuardMessages` вызывался только

## 1.19.9 — 2026-07-24

- **КРИТИЧНО: служебный маркер токенов утекал в видимый автору текст.**
  Живой инцидент: автор увидел `«Добро пожаловать».\n[[LITSOVET:USAGE:{...}]]`

  внутренний маркер, который сервер дописывает в САМ КОНЕЦ потока (реальные
  prompt/completion tokens апстрима, см. USAGE_MARKER_RE в llm.js), а
  callLLM() до сих пор отдавал в `onToken` СЫРЫЕ чанки по мере поступления

  какой-то из потребителей `onToken` (напр. ui/stages.js: живой предпросмотр
  прямо пишет `scene.text=prog.text` во время стрима) успевал показать/
  сохранить чанк ДО того, как маркер был вырезан, он оставался в тексте.
  Теперь callLLM придерживает хвост потока (400 симв. — с запасом длиннее
  любого маркера) и отдаёт в `onToken` только то, что заведомо старше этого
  хвоста; сам маркер физически не может покинуть функцию ни при каком
  разбиении на TCP-чанки. Для очень коротких ответов (<400 симв.) живая
  «печатающая» анимация пропадает (текст приходит одним куском в конце) —
  осознанный компромисс ради гарантии, что маркер никогда не утечёт.

отдельный вопрос: почему персонаж-ИИ в сцене физически сидит на
подоконнике, а Стражи молчат.

- **Эскалированную находку больше нельзя навсегда заглушить одним отказом.**
  Фильтр «замечание уже мотивированно отклонено» (pipeline.js) читал
  `flags` ДО подсчёта эскалации — значит `rememberRejected()` стирал
  находку из `flags` раньше, чем эскалация на следующей итерации вообще
  успевала её увидеть. Теперь находки, уже достигшие порога эскалации
  (`FACTUAL_ESCALATE_ITERS`), исключены из фильтра отказов — они продолжают
  оставаться в `criticals` каждую итерацию, пока не будут реально
  исправлены в тексте или не закончатся итерации (тогда видны автору через
  флаги сцены, а не пропадают молча).
- **Причина, почему «ИИ сидит на подоконнике» прошло незамеченным**:
  скрытая природа персонажа существовала только в синопсисе автора —
  Книжный архитектор читает канон, но никогда не пишет в него, а Стражи
  видят только structured-факты (`state.bible`/`state.characters`), не
  сырой синопсис. До первой сцены с этим персонажем нечего было сверять.
  Добавлена универсальная категория «персонажи» в «Мир» (актуальна для
  любого жанра, не только фэнтези/фантастики) — акцент на скрытой природе,
  которая физически ограничивает то, что персонаж может делать в сцене.
  На вкладке «Структура» — баннер-подсказка ДО построения скелета (если
  есть синопсис, но фактов о персонажах ещё нет): один клик «Найти факты о
  персонажах» предлагает кандидатов через тот же канал одобрения, что и
  «недостающие факты» Архитектора.

## 1.18.0 — 2026-07-23

Прицельный разбор Книжного архитектора (`architect-book.js`, все ~740 строк
прочитаны сплошняком) по просьбе автора — 3 новых, подтверждённых находки
за пределами уже исправленного targetWords-клэмпа:

- **«Точечная правка» (structurePatchMode) молча теряла написанную прозу.**
  При патче главы, где сцены уже написаны, `applySkeletonPatch` создавала
  для неё совершенно новые узлы сцен (`text:''`, новый id) — старый текст
  исчезал без резервной копии, хотя `regenerateChapter`/`regenerateDownstream`
  (тот же по сути шаг) уже давно защищают именно этот случай через
  `proseVersions`. Теперь патч переиспользует старые узлы сцен позиционно —
  план обновляется, текст (если был) уходит в `proseVersions`.
- **Недописанный ответ модели молча оставлял «хвост» нетронутым.**
  `regenerateChapter`/`regenerateDownstream` оба просят модель переписать
  ВСЕ сцены (главы/хвоста), но не гарантируют получить их все — если ответ
  короче, «лишние» сцены раньше оставались со старым (уже противоречащим
  новой правке) брифом и прозой без единого сигнала автору. Теперь такие
  сцены помечаются ⚠ (`stale`, тот же значок, что уже используется для
  «сцена выше изменилась»), а статус-строка каскадной перегенерации честно
  называет недостачу.
- **Промпт точечной правки не знал двух ключевых правил полной генерации.**
  «НЕПРЕРЫВНОСТЬ ЗНАНИЙ ГЕРОЯ» и «ПЕРВАЯ СЦЕНА КНИГИ» жили только в
  `bookArchitectMessages` — при этом Оценщик структуры может явно
  смаршрутизировать находки «Неоткуда знать»/«Ставки первой главы» именно
  в точечную правку через `affectedChapters`, и чинить их приходилось без
  единой инструкции, зачем вообще искать источник знания или что первая
  сцена особая. Оба правила вынесены в общие константы, подключены в обоих
  промпт-билдерах (второе — только когда патч реально затрагивает главу 1).

## 1.15.0 — 2026-07-23

Разбор статистики 44 реальных вердиктов Оценщика показал, что 3 из 6 осей
рубрики (свежесть, конкретика, темп) практически заморожены на средних
значениях (LLM-as-judge central-tendency bias при отсутствии эталона для
сравнения) — арифметический потолок «личного лучшего» по каждой оси даёт
7.29, что ниже порога принятия 7.5. Плюс кросс-сценовые проблемы (повтор
одного и того же комедийного приёма, пассивность героя, однообразная подача
экспозиции), которые не видны ни одному агенту, читающему только одну сцену
за раз. Все изменения сделаны жанронезависимыми — инструмент не подгоняется
под конкретную книгу.

- **Калибровка Оценщика по осям без внешнего эталона.** Freshness/Concrete/
  Pace получили few-shot примеры (3/6/9, жанронейтральные иллюстрации) и
  правило «мост между цитатами и баллом» (0 цитируемых проблем → ≥6, 2-3 →
  ≤6; балл 5 как ленивый дефолт запрещён явно). Freshness видит уже
  использованные в этой книге клише (`usedCliches`), Pace сравнивается с
  медианой длины уже принятых сцен этой же книги (самореференция, не
  жанровый норматив).
- **Отслеживание пассивности героя** — переиспользует существующий вопрос
  Читателя-стража («герой пассивен?») без нового вызова LLM; систематическая
  пассивность (≥3 из последних 6 сцен) всплывает в отчёте Критика.
- **Новый детектор кросс-сценовых приёмов** (`src/craftsignals.js`) —
  извлекает структуру комедийных/напряжённых битов сцены (закрытые категории
  setup/style) и СВОБОДНУЮ метку источника (`channel`), которую называет сама
  модель под конкретную книгу — не завязано на фиксированный список тропов
  вроде «ИИ-спутник», работает для любого жанра/приёма. Группировка по
  нечёткому сходству меток (TF-IDF/cosine, как в bible.js). Отчёт Критика
  показывает: повторяющийся приём (≥4 раз), доминирование одного источника
  экспозиции (≥60% сцен с экспозицией).

## 1.14.0 — 2026-07-23

Найдено и починено при полном редакторском чтении книги (обрыв сцен на
полуслове) и последующем разборе, почему целевая правка не поднимала балл.

- **Обрыв стрима токенами/сетью маскировался под штатное завершение.**
  `server.js` глотал ошибку оборванного апстрим-соединения пустым `catch{}`
  — клиент получал формально успешный ответ и не мог отличить обрыв от
  нормального конца. Теперь сервер помечает обрыв маркером в теле ответа,
  `llm.js` ловит его и ретраит как обычную сетевую ошибку.
- **`looksTokenTruncated` не была подключена к ветке правки черновика** —
  самому частому пути сцены по пайплайну. Теперь обрыв не может победить в
  отборе `best` ни в одной ветке (с/без Оценщика, авто/эскалация).
- **Токенные бюджеты прозы были занижены** относительно реальной плотности
  (~2.78 ток/слово по факту против заложенных 2.5). Прозаик/Линейный
  редактор: 2.5→3.5 ток/слово, потолок правки 5000→11000, потолок ретрая
  первого черновика 8000→16000.
- **`opts.directive` (целевая правка по конкретным находкам) терялась после
  первой итерации** — в конце каждой итерации директива полностью
  перезаписывалась текстом, собранным заново только из ТЕКУЩИХ находок
  Стражей/Оценщика. Теперь «стоячее» указание домешивается в директиву на
  каждой итерации, а не только на первой.
- **Потолок правки масштабировался только от длины прозы**, не от объёма
  критики — теперь растёт вместе с длиной директивы (запас под текст
  [РАЗБОР], а не только под переписанную прозу).
- **Реальный `usage` от апстрима теперь долетает до клиента**
  (`stream_options.include_usage`) — токен-учёт и остальные бюджетные
  решения опираются на факт, а не на клиентскую оценку `estimateTokens`.
- **Оценщик реально упирался в лимит токенов** (живой факт: `tokensOut`
  ровно на заявленных 1950 → JSON обрывался → вердикт не парсился). Лимит
  поднят (1950→3200), добавлен один ретрай с удвоенным лимитом при провале
  парсинга.
- **Нераспарсенный вердикт Оценщика мог выиграть отбор `best`** только за
  счёт отсутствия критических флагов Стражей — сцена уходила в книгу без
  реальной оценки качества (`lastEval.ok:false`), а не с низкой оценкой.
  Теперь `verdict.ok` — обязательное условие «чистого» черновика.
- Добавлен `GET /api/version` — сверка задеплоенной версии без открытия UI.
